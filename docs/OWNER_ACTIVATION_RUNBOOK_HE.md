# הפעלת בעלים ורישיונות Björken — הוראות מפעיל

תאריך: 25.10.2026. הקוד הוכן בענף `fix/bjorken-reviewed-pilot-v2`, מעל תיקוני המחשבון והקישור הציבורי. **מסמך זה אינו אישור פריסה. לא בוצעו פריסה או הקמה ב־Atlas במסגרת השינוי.**

## המצב וההסכמות

- חשבון היעד: `bjorken-owner`. סיסמה חזקה זמנית תיווצר **בעת ההקמה במסד המאומת**, תוצג פעם אחת ותוחלף בכניסה הראשונה. אין סיסמת פרודקשן חדשה למסור בשלב הכנת הקוד.
- היעד ל־WhatsApp שאושר בידי המזמין: `0504453592`. זה המספר האישי/הניסיוני שבחר לקבל אליו בקשות בפועל. לא הוחלף טלפון הקשר של המאפייה.
- המזמין אישר שימוש מסחרי בתמונות הקיימות במסגרת אישור התוכנית. כלי ההפעלה מתעד את האישור; הבדיקות לא בדקו זכויות מול צדדים שלישיים.
- רישיונות Food Pro, Group Delivery, Club, Reviews, Analytics לשנה קלנדרית ממועד ההפעלה. Orders Pro נכלל ב־Food Pro. אין פעולת גבייה.
- בקשה רגילה יכולה לכלול מחיר לא ידוע. אין להמציא מחיר מוצר, לאשר קטלוג בשם הבעלים או לבצע הזמנת בדיקה באתר החי.
- במסד המקומי שנבדק קודם נמצא `bjorken_dev`. זה **אינו מוכיח** שהוא המסד המשרת את Vercel Production.

## אימות Vercel לפני כל כתיבה

1. לקבל גישת ניהול לפרויקט שמשרת בפועל את `https://bjorken-bakery.vercel.app`. הוצע חיבור Vercel; החיבור לא הושלם בזמן הכנת הגרסה.
2. לרשום מזהה צוות/פרויקט, Deployment הפעיל, SHA של הקוד, כתובות הדומיין והגדרות Build. לוודא שאין זה פרויקט Cotta או HASI הראשי.
3. לבדוק ב־Production את `MONGODB_URI` או `MONGO_URI` ואת `MONGO_DB_NAME`: אותו cluster ו־DB ייעודי ל־Björken. להשוות את היעד לערכים המקומיים בלי להעתיק URI/סיסמאות לדוחות, Git או הודעות. אם שני משתני URI קיימים, `MONGODB_URI` קודם; יש להסיר עמימות.
4. לבדוק זמינות Mongo replica set/Atlas והרשאות קריאה/כתיבה/transactions. לבדוק `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_UPLOAD_PRESET`, ואת `NEXT_PUBLIC_SITE_URL=https://bjorken-bakery.vercel.app`. אין צורך בסיסמת בעלים במשתני Vercel אחרי ההקמה במונגו. TOTP נשאר אופציונלי; אם מוגדר, נדרש גם קוד מאמת בכניסה.
5. לצלם לעצמכם את מזהה הפריסה הקודמת ולוודא גיבוי Atlas תקין. לא לייצא רשימות לקוחות או hashes לתיקיית קוד.
6. להציג למזמין גרסה, תוצאות בדיקות, היעד ודרך חזרה; לקבל **אישור פריסה נפרד**. התוכנית שאושרה אינה מסירה דרישה זו.

אפשר להריץ `npm.cmd run owner:inspect` לאחר הזנת סביבת היעד המאומתת. זוהי קריאה באמצעות MongoClient, ללא seed, יצירת אינדקסים, שינוי בקשות או חשיפת hash. הפלט מציג host, שם DB, קיום בעלים, מספר מוצרים מתומחרים ותוקף הפעלה; אינו מאמת בעצמו את הקשר לפרויקט Vercel.

## שילוב ופריסה לאחר אישור

1. לשמור את תיקוני הענף ב־commit מקומי ולוודא `git status -sb` נקי. הבסיס בזמן העבודה הוא `593886c`; `main` הוא `33f7470` ואב קדמון של ענף התיקונים. אין לבצע reset או force push.
2. לאחר אישור לפרסום, לשלב ב־`main` ב־fast-forward אם הוא עדיין אב קדמון, או PR אם התקדם. אין לדחוף `main` לפני האישור: Git integration יכול לפרוס אוטומטית.
3. לפרוס את ה־SHA שנבדק לפרויקט המאומת. לאשר שה־Deployment והדומיין מצביעים אליו; לרשום `dpl_…` ו־`prj_…` אמיתיים.
4. בשלב יצירת הבעלים אפשר להשאיר `BJORKEN_ENABLE_LIVE=false`. לפני הפעלת בקשות אמיתיות לוודא את ערכו בפריסת היעד. כלי ההפעלה בודק גם דגל LIVE וכתובת קנונית בסביבת המפעיל, אך אינו משנה משתני Vercel.

## כלי ההקמה המוגבל

אין endpoint ציבורי לרישום מנהל. הכלי רץ בטרמינל של מפעיל מורשה, מה־commit הנבדק כשהעץ נקי ובסביבת Mongo שאומתה מול Vercel. ללא `--apply` הוא קורא בלבד. `--apply` חסום ללא רישום אישור טרי שתואם ליעד. הרישום הוא הצהרת המפעיל לאחר אימות אמיתי, **אינו תחליף לאימות מול Vercel**.

לאחר האישור בלבד יוצרים `.local/production-approval.json` (מוחרג מ־Git) בערכים אמיתיים:

```json
{
  "businessId": "bjorken",
  "productionDeploymentApproved": true,
  "vercelTargetVerified": true,
  "projectId": "prj_REPLACE",
  "deploymentId": "dpl_REPLACE",
  "siteUrl": "https://bjorken-bakery.vercel.app",
  "mongoHost": "REPLACE.mongodb.net",
  "mongoDatabase": "REPLACE",
  "reviewedCommit": "REPLACE_WITH_40_CHARACTER_SHA",
  "approvedAt": "REPLACE_WITH_ACTUAL_APPROVAL_TIME_ISO",
  "reference": "REPLACE_WITH_APPROVAL_REFERENCE",
  "whatsapp": "0504453592",
  "imagesApproved": true
}
```

התבנית אינה אישור תקף. הכלי דורש אישור שניתן ב־24 השעות האחרונות, שם מסד מותר, מזהי פרויקט/פריסה, התאמת commit ועץ נקי. `--local-test` עוקף רק את אישור הפרודקשן ורק עם שרת Mongo ב־loopback ומסד בשם `bjorken_test`.

1. יצירה: `npm.cmd run owner:setup -- --apply --phase owner --approval-file .local/production-approval.json`.
2. להעביר לבעלים את הסיסמה הזמנית מהפלט בערוץ מאומת. לא לשמור אותה בקובץ מתועד, סביבת Vercel או דוח. אם יש בעלים קיים הכלי מחזיר `created:false` ללא סיסמה ואינו משנה אותו. גם רשומת hash ישנה לא תידרס.
3. הבעלים נכנס ל־`/admin/modules`, מנותב ל־`/admin/security`, מחליף לסיסמה אישית של לפחות 12 תווים עם אותיות ומספר/סימן, ומתחבר מחדש. כל החיבורים הקודמים מתבטלים. אין לבקש מהבעלים למסור לכם את סיסמתו האישית.
4. לאחר כניסה מוצלחת והחלפה: לוודא LIVE וכתובת אתר בסביבת הפריסה ובסביבת המפעיל. להפעיל `npm.cmd run owner:setup -- --apply --phase activate --approval-file .local/production-approval.json`.
5. לשמור במסירה את `startsAt` ו־`expiresAt` שהכלי מחזיר. פעולת הפעלה חוזרת אינה מאריכה את השנה ואינה פותחת מחדש הגדרות שהבעלים סגר לאחר מכן. ההפעלה אינה משנה מחירי מוצרים, זמני איסוף או `catalogApproved`. אם תאריך סגירת הבקשות כבר עבר, היא חסומה עד שהמפעיל יבדוק אותו.
6. אם הסיסמה הזמנית אבדה, אפשר אחרי אישור יעד תקף לבצע `--phase reset-owner`. זו פעולה מפורשת שמחליפה סיסמה זמנית ומנתקת sessions; אינה דורסת זהות או רישיונות. סיסמה קודמת אינה ניתנת לשחזור.

במונגו נשמרים salt ו־scrypt hash, שם משתמש, דגל החלפה, גרסת אימות ותאריכים בתוך `configs`, במפתח `hasi:bjorken:ownerAuth`. sessions נשמרים בנפרד ב־`staffsessions`. יצירה, איפוס ושינוי סיסמה מתועדים ללא סיסמאות. שינוי סיסמה שומר את שם המשתמש ומטא־נתוני ההקמה. גרסת אימות מונעת שימוש גם בחיבור מנהל ישן ללא שיוך עסק.

## רישיונות ונתוני הפעלה

`hasi:bjorken:licenses` שומר את הזכאויות והתוקף. `hasi:bjorken:activationV1` שומר את מועד ההפעלה, האסמכתא, אישורי WhatsApp/תמונות ואת הגדרות/רישיונות הקדם לצורכי התאוששות. זה אינו שינוי ב־HASI הראשי או ברישוי עסק אחר. אין עותק כפול בתשלום ל־Orders Pro ואין ספק סליקה שמחויב.

בעלים יכול לנהל את כל המסכים. מוכר, אופה ושליח שומרים על מגבלות התפקיד; רישיון אינו הופך אותם למנהל. עלויות מוצר, תחזיות ורווחיות נשארות חסומות בחנות הבסיסית או ללא רישיון מתקדם.

## בדיקת קבלה באתר החי

כניסה והחלפת סיסמה הן הפעולות הנדרשות להפעלת החשבון. אחריהן לבצע בדיקות קריאה בלבד: מסכי ניהול, זכאויות ותוקף, קטלוג ציבורי, WhatsApp בקישורי קשר, שעות, תמונות ופרטי קשר. לא ליצור לקוחות, קופונים, הזמנות או מסלולי דמה ב־Production. לא ללחוץ „שליחה” ב־WhatsApp במסגרת בדיקה.

כל עשרת המוצרים שנבדקו קודם היו ללא מחיר. אפשר לקבל עבורם בקשות איסוף רגילות באישור מחיר ידני; כדי לקבל משלוח קבוצתי הבעלים צריך להזין מחירים מספריים למוצרים שיימכרו במסלול. מסך המסלולים מציג הודעה וקישור לעריכת המוצרים כל עוד אין אפילו מוצר מתומחר. המוצרים חסרי המחיר אינם מוצגים לבחירה בדף מסלול. אין לפרסם מסלול לקהל כשאין בו מוצרים למכירה.

## דרך חזרה

1. במקרה של תקלה תפעולית לסגור תחילה „בקשות פתוחות” ב־`/admin` ולפי הצורך `BJORKEN_ENABLE_LIVE=false` בפריסה. לא לבטל הזמנות אמיתיות או למחוק נתונים כחלק מחזרה.
2. אם התקלה בקוד, לבחור ב־Vercel את הפריסה הקודמת המאומתת. **חזרה לקוד ישן שאינו תומך בשם המשתמש במונגו עלולה להחזיר תלות בפרטי סביבה.** יש להעדיף תיקון קדימה על בסיס גרסה זו, ולהכין גישת מפעיל לפני שחוזרים לגרסה כזאת.
3. המידע נשאר תואם: נוספו שדות אימות וקונפיגורציות, ללא הסרת סכמות, products או orders. אין להחליף את כל המסד בגיבוי אחרי קבלת הזמנות חדשות. טיפול בשחזור DB דורש תיאום נפרד.
4. אפשר להשבית מודול דרך ניהול רישיון; ההשבתה אינה מוחקת מידע. snapshot של הגדרות קודמות נמצא ברשומת ההפעלה למפעיל בלבד; לא לשחזר אותו אוטומטית מעל עריכות חדשות של הבעלים.

## מה פעיל ומה מחכה לספק

ניהול, התמדה במונגו, הרשאות, סל, שמירת בקשה, פתיחת WhatsApp ידנית, מסלולים, צוות, מועדון, משוב ודוחות פועלים בקוד ובבדיקות. הפעלתם במסד הייצור ממתינה לשלבים לעיל. Cloudinary דורש חשבון/preset תקינים בסביבת הפריסה. `mailto:` פותח תוכנת דואר ואינו ספק דיוור. סליקה, החזרים אוטומטיים, SMS, WhatsApp Business API, Push, GPS וניתוב חי אינם מחוברים; אין להציגם כפעילים.
